# Two Couches

A private shared watchlist and movie-night calendar for two people who live in different countries. For any film or series it shows which streaming services carry it in each person's country, and highlights titles both people can watch.

This repo is public. Never commit personal details: real names, emails, which countries or cities the two users live in, or anything from `CLAUDE.local.md` or `two-couches-plan.html` (both local-only and git-ignored). Use neutral examples in code, tests and docs (`one@example.com`, `GB`, `NZ`). If `two-couches-plan.html` exists locally, read it before starting a new sprint.

- Watch room on a bad connection (2026-11-06, in-session, after the first real night was glitchy with one partner on a poor connection): the hosted gateway logs showed that partner's computer never renewed its 1-hour token during the film (no `/auth/v1/token` request from it for 3 hours), so its room channel was closed by Realtime at expiry and nothing rejoined it (realtime-js doesn't resubscribe after a server close). Now the room rejoins by itself (backoff 1 s to 30 s, also on `online` and when the tab becomes visible), each attempt starting with `getSession()`, which renews an expired token. Sync is gentler: ticks that took over 2.5 s to arrive or were sent before your own last action are skipped; no tick is followed until the clocks have been compared (5 quick pings on joining); under 0.3 s apart is left alone, up to 1.5 s is a speed change of at most 5% (was 10% from 0.2 s), and a jump needs two ticks in a row over 1.5 s. The one in charge also ticks while paused (a lost pause still arrives) and, after a reconnection, announces its state instead of asking (asking made it follow a screen that had missed its pause); `sync` carries `actedAt` so whoever acted last stays in charge. The side panel shows the measured delay to the partner. ## Stack (decided)

- **Language:** TypeScript everywhere.
- **App:** Next.js (App Router) + Tailwind CSS, built as an installable PWA.
- **Hosting:** Vercel Hobby plan (free), deployed from GitHub.
- **Backend:** Supabase Free plan: Postgres, Auth, Realtime, scheduled jobs (pg_cron).
- **Movie/TV data:** TMDB API. Per-country availability comes from TMDB's `watch/providers` endpoint (JustWatch data).
- **Optional later:** Streaming Availability API or Watchmode (deep links, leaving soon).
- **Subtitles:** OpenSubtitles REST API (free account, 20 downloads a day), server only. Added 2026-11-06 with the user's go-ahead.
- **Critic scores:** OMDb API (free key, 1,000 requests a day), server only. Agreed 2026-11-12 for Sprint 23; the user gets the key by hand (omdbapi.com, free tier, activated by email).

Don't add other frameworks or services without discussing it first. Everything must stay within free tiers for v1.

## Rules

### Security
- Never store passwords. Auth is Supabase Auth with Google sign-in or magic links.
- Every table has row-level security (RLS). A user may only read or write rows belonging to their own couple.
- Sign-ups are closed (or limited to an allowlist of two emails) once both users have joined.
- The TMDB key and any other secrets live in `.env.local` and Vercel environment variables. They are used only in server code (route handlers, server actions, cron jobs), never in client components or `NEXT_PUBLIC_*` variables.
- `.env*` is in `.gitignore` from the first commit.
- Never store streaming-service credentials. Profiles store only which services each person subscribes to.

### Data and APIs
- The browser never calls TMDB directly. All TMDB requests go through server routes that add the key and cache results in Supabase for about 24 hours.
- Countries are never hard-coded. Each profile stores an ISO 3166-1 code (`profiles.country`), which is also the TMDB `watch_region`. Fetch providers for both partners' countries.
- "Available in both" means: a subscription (`flatrate`) provider in my country that I pay for, and one in my partner's country that they pay for. Treat rent/buy/free separately.
- Store all times in UTC. Display in each profile's own IANA time zone (e.g. `Europe/London`); zones differ in daylight saving, so never assume a fixed offset between the two people.
- Bilingual UI: the supported languages are `LANGUAGES` in `src/lib/places.ts`. Request TMDB data with the viewer's language and country, e.g. `en-GB`.
- Show TMDB and JustWatch attribution, as their terms require.

### Scope
- The app is a list, a scheduler and a coordinator. It must never host, link to or distribute media files. Synced watching (Phase 2) only stores things like a Syncplay room name, a Teleparty link and "ready" flags. The watch room plays a file each person picks from their own device in their own browser; the file is never uploaded, stored or sent, and only play/pause/position messages travel (decided 2026-11-06).

## Code conventions

- Next.js 16 with `cacheComponents`: anything that reads cookies, the session or `searchParams` renders inside a `<Suspense>` boundary. Don't put per-user data in `use cache`.
- Auth middleware lives in `src/proxy.ts` (Next 16 renamed `middleware` to `proxy`).
- Server-side Supabase: `createClient()` from `src/lib/supabase/server.ts` (acts as the user, RLS applies). `createAdminClient()` bypasses RLS and is only for shared caches like `services`.
- Get the current user with `getCurrentProfile()` / `requireProfile()` from `src/lib/session.ts`.
- TMDB calls go through `tmdbGet()` in `src/lib/tmdb.ts` (server only). Titles and availability are cached in Supabase by `getTitle()` / `getAvailability()` in `src/lib/titles.ts`; search results are throwaway, so `searchTitles()` uses Next's fetch cache (`revalidate`) instead.
- "Who can watch it" rules live in `whoCanWatch()` in `src/lib/watch.ts` (pure, client-safe). Use it rather than re-deriving "available in both".
- TMDB images (posters, logos) use `next/image` with TMDB's own sizes (`tmdbImage()`), never Vercel's image optimisation (quota). Posters (`<Poster>`) go through the custom loader `src/lib/image-loader.ts` (`images.loaderFile`): `src` carries the largest TMDB size and `sizes` the widest it's shown, and the srcset widths (`imageSizes` + `deviceSizes` in `next.config.ts`) are TMDB's widths. Small logos use `unoptimized`.
- Data saver: `src/lib/data-saver.ts` (per device in localStorage, like the theme; `sendDataSaver()` passes it to the worker, which keeps it in the `settings-v1` cache). `public/sw.js` does the work in `poster()`: while `savingData()` it fetches the next size down (`SMALLER`) unless a copy at the asked size is kept; posters are cached by the URL actually fetched. Keep `SLOW`/`savingData()` in step with `isSavingData()`. UI `src/app/settings/data-saver-settings.tsx`.
- Warm-up: `<WarmUp>` (`src/components/warm-up.tsx`, in the layout for paired users) posts to `/api/warm` once the browser is idle, at most every 30 min per device; the route answers 202 and runs `warmCaches()` (`src/lib/warm.ts`) in `after()` as the user. It must ask for exactly what the pages ask for (same TMDB URLs, same availability titles), so it uses Browse's shared `batchPages()` / `popularIn()` (`src/lib/browse.ts`) and `FOR_YOU_CHECKED`; when Browse's or Coming soon's default requests change, change `warmCaches()` too. It starts with `upNext` (the first `UP_NEXT_WARMED` = 30 want/watching titles in Home's order): per-title fetches go in `warmTitlePage()` (the title in the viewer's locale and `getPosterDeck()`), so when the title page starts fetching something new per title, add it there; availability for all of them is one batch.
- Client cache: `experimental.staleTimes.dynamic` is 30 s. Anything that changes data must still refresh (`refresh()` in actions, `<ListSync>`), which also clears it.
- List rules (statuses, category limits, progress, local dates) live in `src/lib/list-rules.ts` (pure, client-safe); list queries in `src/lib/list.ts`; list mutations are the Server Actions in `src/app/list/actions.ts`, which run as the user and call `refresh()`. `episodeAfter(progress, seasonEpisodes)` rolls into the next season (null after the last episode); `nextEpisode()` in `review-rules.ts` takes the counts.
- Live updates: render `<ListSync coupleId>` on any page that shows list data (it also covers reminders, dismissals and watch nights). It subscribes to Realtime as the signed-in user (must `realtime.setAuth()` first, or RLS hides every insert/update) and calls `router.refresh()`. Realtime can't filter deletes, so those are subscribed unfiltered. It also listens to `review_signals`, since RLS keeps `list_reviews` from sending your partner's row until you've written yours.
- pgTAP tests start by clearing users and caches inside their transaction (rolled back), so they pass with local sign-ins present.
- UI text: no hard-coded strings. Each area has a namespace in `src/lib/i18n/` exporting `{ en, tr }` (`tr` typed as `typeof en`); text that varies is a function. Server components call `getI18n()` from `src/lib/i18n/server.ts` (inside `<Suspense>`); client and shared components take a `language` prop and call `getMessages(language)`. In Turkish, never attach a suffix to an interpolated name or country (write "Ekleyen: {name}", not "{name}'ın"). Page-level `<Suspense>` fallbacks are the page's own wordless skeleton (see Loading).
- Browse: discover, trending and genres are in `src/lib/browse.ts` and use Next's fetch cache (6 h; genres 24 h), like search. `getAvailability()` de-duplicates its input and checks at most 20 titles at once against TMDB.
- Alerts: the rules are pure in `src/lib/alert-rules.ts` (`alertFor()`, `reminderDone()`, `describeAlert()` for wording on the page and in pushes). List titles alert only when they become watchable for both; reminders also when one of you first can. "Before" and "now" are both judged by today's services, so changing settings never alerts. When a title is added to the list or gets a reminder, call `recordBaseline()` (`src/lib/alerts.ts`) so the next check compares with today.
- The daily job is `runDailyCheck()` in `src/lib/daily-check.ts`, run by `src/app/api/cron/daily/route.ts`. It uses the admin client (no user), passing it to `getAvailability(…, { client, maxAgeMs })`. Push goes through `sendPush()` in `src/lib/push.ts` (`web-push`; ended subscriptions are deleted); the service worker is `public/sw.js`. To test locally: `curl -X POST -H "Authorization: Bearer $CRON_SECRET" localhost:3000/api/cron/daily`, or put `app_url` = `http://host.docker.internal:3000` and `cron_secret` in local Vault and `select public.request_daily_check()`.
- Coming soon data (`src/lib/upcoming.ts`) uses Next's fetch cache like browse (6 h; release dates 24 h). Use `<TitleCard>` (`src/components/title-card.tsx`) for poster cards; pass `availability: null` to skip badges.
- Actions that need a couple use `requireCoupleProfile()`; saving a title for the couple goes through `cacheForCouple()` (caches both partners' locales first) in `src/lib/list.ts`.
- `src/proxy.ts` lets `/api/cron`, `/sw.js` and `/manifest.webmanifest` through without a session.
- For you: seed weights and scoring are pure in `src/lib/recommend-rules.ts` (`seedWeight()`: each rating counts from 3★, so split opinions cancel and shared 4★+ get a bonus; unrated list titles count a little, dropped ones against; `scoreSuggestions()`, `rankForCouple()` boosts by `whoCanWatch()`). `getForYou()` in `src/lib/recommend.ts` fetches recommendations with Next's fetch cache (24 h), excluding list and dismissed titles. - Subscription advisor: pure in `src/lib/advisor-rules.ts` (`adviseServices()` runs `whoCanWatch()` with each candidate service added; `showcase()` picks posters); `src/app/settings/advisor.tsx` uses home countries, saved services and `getAvailability()` only.
- Calendar feed: `src/app/calendar/[feed]/route.ts` has no session (`/calendar` is in `PUBLIC_PATHS`, so anything added under it is public). It hashes the token (`token.ts`, `node:crypto`) and `feedCalendar()` (`feed.ts`) looks it up with the admin client, then reads only that owner's couple; malformed and unknown tokens get a 404. `toIcs(events, feed?)` in `night-rules.ts` takes a list of `IcsEvent`s (with `feed` it adds the calendar name and refresh hints; `FEED_REFRESH_MINUTES`, `FEED_DAYS_BEHIND`, `FEED_DAYS_AHEAD`); UID `<night id>@two-couches`. A night's event text is built only by `nightEvent()` (`src/app/calendar/night-event.ts`), used by the feed and `/watch-nights/[id]/ics`. Actions `makeCalendarFeed()` (returns the token once) / `stopCalendarFeed()`; UI `<CalendarSubscribe>` builds links from `window.location`; text under `nights.calendar`.
